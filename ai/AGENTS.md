# グローバル指示

Claude Code・Codex・Muse が全セッションで読み込む個人指示（dotfiles の `ai/AGENTS.md`。`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`、`~/AGENTS.md`（Muse の運用ファイル）はここへのリンク）。
プロジェクト固有のことは各リポジトリの `CLAUDE.md` / `AGENTS.md` に書く。

## 言語・トーン

- 応答は日本語。コード内のコメント・識別子は英語のまま。
- 不要な前置きや結論の繰り返しは省く。簡潔に。
- 「やりました」「完了しました」のような決め台詞よりも、何が変わって次に何をするかを 1〜2 文で。

## 作業の進め方

- 推測で作業せず、不明点は早めに聞く。ただし軽微な選択は自分で判断して進める。
- 既存ファイルの編集を優先。新規ファイルは必要なときだけ。
- 変更は小さく刻む。一度に複数の関心事を混ぜない。
- 動作未確認のものを「動く」と言わない。試したか／試していないかを明示する。

## コードスタイル

- コメントは「なぜ」を書く必要があるときだけ。「何をしているか」は識別子で表現する。
- 後方互換のための半端なシム・未使用変数のリネーム（`_var`）を残さない。不要なら削除。
- エラーハンドリングは境界（外部 API・ユーザー入力）でだけ。内側で防御的に書かない。

## Git

- リポジトリに記録するのは決定事項だけ。未決定の案・検討メモ・調査資料はローカルに留める。
- コミットは 1 つの変更がまとまった時点でその場で切る（あとでまとめない）。
- メッセージは英語。件名は `add:` / `update:` / `fix:` / `docs:` + 大文字で始まる命令形（既存の log に倣う）。本文には何をしたかを箇条書きで列挙し、必要なら理由を添える。PR も英語で、変更点を列挙する。
- 自分が書いた変更には `Co-Authored-By: <モデル名とバージョン> <アドレス>` を付ける。subcon で委任した変更は `subcon guide` の規則に従う（実装者が Co-Authored-By、自分は Reviewed-By。自分も手を入れたら両方）。
- レビューを経た変更には `Reviewed-By: <モデル名とバージョン> <アドレス>` を付ける。他の AI（Codex など）にレビューさせたらそのモデル、自分が他者の変更を検収してコミットするなら自分。
- 次は必ず確認を取る: `--no-verify`、`--force`（`push --force` 含む）、`reset --hard`、`branch -D`、本番反映、データ削除。

## バージョン管理

- `Cargo.toml` / `package.json` / `pyproject.toml` などのバージョンは、変更内容に応じて適宜上げる。聞かずに上げてよい。
- 上げ方は semver に従う:
  - **patch** (`0.1.0` → `0.1.1`): バグ修正、内部リファクタ
  - **minor** (`0.1.0` → `0.2.0`): 後方互換のある機能追加
  - **major** (`0.1.0` → `1.0.0`): 破壊的変更
- 0.x 系では、破壊的変更なら minor、機能追加・修正なら patch を上げる。
- バージョン更新は機能変更と同じコミットに含める（別コミットにしない）。

## ツール使い分け

- ファイル探索は速い方を選ぶ。デフォルトは ripgrep (`rg`) / `fd`（`grep` / `find` より速い）だが、より効率的な手段（IDE のインデックス、専用 CLI、プロジェクト固有の検索スクリプト等）があればそちらを優先。
- 広範な調査だけサブエージェント（Claude Code の Explore など）に任せる。
- 並列化できるツール呼び出しは同じメッセージ内でまとめて呼ぶ。

## タスクの順序（許可待ちで止まらない）

着手前にタスクを「許可不要」「許可必要」の 2 群に分け、許可不要のものから片付ける。

- **許可不要の例**: 既存ファイルの編集、ファイルの読み取り・検索、ローカルでのテスト実行、`git status` / `git diff` / `git log`
- **許可必要の例**: 新規パッケージのインストール、外部 API 呼び出し（ユーザーが頼んだ流れの中での subcon や他モデルへのレビュー依頼は除く）、課金が発生する操作、`git push`、`gh pr create`、本番への反映

判断方針:

- 許可が必要そうなタスクは、可能な限り後ろにまとめる。途中で個別に聞かない。
- 1 つの許可待ちで他のタスクが止まらないよう、独立して進められるものを先に終わらせる。
- 最後に「許可が必要なものリスト」をまとめて提示し、一度に承認してもらう。

## レビュー

- 設計 doc と、大きめの変更をマージする前は、別系統のモデルに読み取り専用でレビューさせる。Claude なら Codex、Codex なら Opus。
  - Codex: `codex exec -s read-only -o <出力ファイル> "<依頼>" < /dev/null`
  - Opus: Claude Code ならサブエージェント（model: opus）。それ以外は `claude -p --model opus --permission-mode plan "<依頼>"`
- 依頼には対象・観点・「ファイルを変更しない」・出力形式（重要度付き、該当箇所と修正案）を書く。
- 指摘は鵜呑みにせず仕分けて反映し、そのコミットにレビュアーを `Reviewed-By` で入れる。

## Flash への実装委任

原則は自分で実装する。複数ファイルにまたがる新規実装で、作業票（触るファイル・インターフェース・合格条件）が事前に書け、失敗しても diff を捨てるだけで済むときだけ、`subcon submit` で Gemini Flash に渡す。
委任する前に `subcon guide` を読み、その手順（作業票の書式・検収・コミットの trailer）に従う。
