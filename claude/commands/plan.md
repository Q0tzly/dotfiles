`$ARGUMENTS` について、実装計画だけ立ててください。コード変更はしない。

成果物:

1. **目的**: このタスクが何を解決するか、1〜2 行。
2. **現状調査**: 関連するファイル・関数を `path:line` 形式で列挙。Grep/Glob で実際に確認すること。
3. **設計**:
   - 変更するファイルと、それぞれで何を変えるか
   - 既存の関数・ユーティリティで再利用できるもの
   - 新規追加が必要な型・関数
4. **手順**: 上から順に実行する形でタスク分解。各タスクは独立して検証可能な粒度に。
5. **テスト方針**: どう動作確認するか（既存テスト追記 / 新規 / 手動）。
6. **未確定事項**: 仕様の曖昧な点、判断が必要な分岐があれば明示。

ルール:

- 既存パターンを優先。新しい抽象は本当に必要なときだけ提案する。
- 「だいたいこんな感じ」では終わらせない。具体的なファイル名・関数名まで落とす。
- 推測で書かず、コードを読んで確認した内容だけ書く。
